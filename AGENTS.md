# AGENTS.md — правила проекта

## Проект

«Система субтитров с определением говорящего для умных очков». УрФУ, ИРИТ-РТФ, программа поддержки талантливых первокурсников, 2026/2027. Ментор — Летавин Д. А. Дорожная карта v2 утверждена 20–22.10.2026, сроки 10.10.2026–30.06.2027.

Цель: человек с нарушением слуха видит в умных очках субтитры речи выбранного собеседника с небольшой задержкой. До января обязательны потоковое русское ASR, опыт диаризации 2–3 говорящих, WER/задержки, отчёт и демонстрация. ASD — предварительная проверка, не гарантированный результат.

## Жёсткие факты (смотреть здесь, а не переспрашивать владельца)

**Оборудование:** i7-11700KF, 64 ГБ DDR4, AMD RX 7700 XT 12 ГБ, Windows.
CUDA нет и не появится: это технология NVIDIA. GPU-ускорение здесь означает
DirectML / ROCm / Vulkan — ветку, которая **не проверялась**.
Проверено 12.11.2026: в `.venv` `onnxruntime 1.31.1` с провайдерами только
`CPUExecutionProvider` и `AzureExecutionProvider`; `torch` и `pyannote` не
установлены; `sherpa-onnx 2.0.1` принимает только `provider=cpu|cuda|coreml`,
то есть GPU-пути для AMD на Windows у него нет. Для опыта с GPU нужен отдельный
venv с `onnxruntime-directml` (он заменяет пакет `onnxruntime` — в `.venv` не ставить).

**Измерено (артефакты и детали — в `STATUS.md`):** WER FLEURS ru, 50 клипов:
sherpa-onnx 11.35 %, Vosk 18.92 %. T1 — CPU/RSS на одном прогоне; T2 — 5 клипов
× 4 условия; endpointing p50 509 / p95 995 мс (Vosk, синтетическая речь, n=8);
наивная диаризация 0.516 — метрика сломана, это не DER.

**Обязательства до января (сжатая карта):** потоковый русский ASR; опыт
диаризации 2–3 говорящих на записях; таблицы WER и задержек; аналитический отчёт
до 25.11 и демонстрация. ASD — предварительная проверка, не гарантия.
Сравнение on-device / cloud / edge / hybrid — «позже» по `PROJECT.md` §4, на январь
не требуется.

**Решения по умолчанию:** CPU — гарантированный путь прототипа; GPU/DirectML и
облако — измеряемые альтернативы, а не догма (`ADR-0002`). Менять только через ADR.

**Чего нельзя заявлять без замера:** сквозную задержку «микрофон → экран», работу
на физических очках, gaze, live-ASD, идентификацию личности и выигрыш/проигрыш
против облака, если сравнение не проводилось.

**История изменений:** git инициализирован 12.11.2026 (см. `STATUS.md`).
Историю до инициализации по git восстановить нельзя; коммит не доказывает запуск.

**Приоритет и актуальность:** перед проектной задачей используй `docs/agent-context.md`.
Обязательства — подписанный PDF и дословные таблицы `docs/scope.md`, не сокращённый
`ROADMAP.md`. `temp/ревью.txt` — предложения и непроверенные внешние утверждения,
не принятые изменения карты. Разделы STATUS с датами — исторические снимки;
категоричные выводы об отсутствии аналогов/данных требуют отдельной проверки.

## Главное правило

Не выдавай источник за измерение. Всегда разделяй:
- **источник** — что написано в документации/статье;
- **план** — что мы собираемся сделать;
- **измерено** — что реально получено на нашем оборудовании, с командой и логом.

Если эксперимента не было, пиши «не запускалось». Если метрика не измерена, пиши «не измерялось».

### Сопоставимость метрик

Одно и то же число в разных условиях ничего не значит. Поэтому:

- любое наше число публикуется только с условиями: датасет, n, домен (чтение/диалог/дальнее поле), шум, нормализация, определение метрики, спикер-агностик или атрибуция;
- сравнивать с чужим числом можно только при совпадении этих условий; иначе писать «не сопоставимо» и указывать, что нужно для корректного сравнения;
- реестр — `docs/benchmarks.md`: новое измерение добавляет туда строку, новое внешнее число — строку с ответом «что нужно, чтобы сравнение было честным»;
- отдельно запрещено: наше чтение без шума против чужого диалога, «точность по кадрам» против DER, наша задержка «чанк → выдача» против маркетинговых «300 мс».

## Роли

- `assistant` — дешёвый интерфейс по умолчанию: простые вопросы, статус, напоминания, маршрутизация. Код не выполняет.
- `mentor` — старший ментор: сложные задачи, архитектура, код, проверка. Может быть primary (`/mentor`) или субагентом.
- `researcher` — поиск и проверка фактов, документации, статей, лицензий. Возвращает бриф со ссылками.
- `digester` — сжатие длинных текстов и логов без новых фактов.
- `reviewer` — критическая проверка отчёта, методики, кода и лицензий. Ничего не правит.
- `implementer` — код и эксперименты, запуск тестов, фиксация результатов.
- `vision` — изображения, кадры, видео, ASD.

## Как работать

- По умолчанию сессия идёт в `assistant` — это дешёвая модель для вопросов, напоминаний и навигации. Это нормальный режим, не «режим плохой модели».
- Для сложной задачи используй `/mentor` — сессия переключится на старшего ментора. Вернуться: `/assistant`.
- Можно не переключаться: попроси ассистента «вызови ментора» — он позовёт `mentor` как субагента для одного сложного вопроса.
- Если нужна полная оркестрация (код, ревью, видео, несколько специалистов) — используй `/mentor`: в режиме субагента ментор работает как советник и не запускает других субагентов.
- Длинные операции (установка пакетов, скачивание моделей, обучение, прогон на длинном аудио) — в `/mentor` primary, не через субагента. Субагент годится для короткой проверки, но не для многошаговой установки.
- Вручную менять модель через `/models` нужно только если хочешь конкретную модель. Для обычной работы это не требуется.
- «Где мы остановились?» — читается `STATUS.md`. После значимой сессии обнови его.
- Если ассистент не справляется или вопрос важный — переключайся на `/mentor`, не пытайся «дожать» дешёвой моделью.

## Ночная автономная система

`autonomy/` запускается только по прямой команде владельца. Никаких задач планировщика, автозапуска и триггеров на старт: пока владелец не сказал «запускай», не запускать ничего. После ручного старта непрерывность держит супервизор `autonomy/scripts/run_loop.ps1`, который повторяет `tick` до `DONE`. Запуск: `start_night.ps1`, остановка: `stop_night.ps1`. Задачу `OpenCodeGlasses-NightRunner` и `install_trigger.ps1` не восстанавливать. Перед выполнением план проходит критика (`autonomy/critic.py`, модель отличается от планировщика, максимум 2 раунда правок); вердикт `block` останавливает ночь и выносит решение владельцу. Критик может проверить внешний факт поиском (до 3 запросов, один раунд) — найденное остаётся источником, а не измерением; одобрение привязано к содержимому плана, поэтому правка задач руками снова отправляет план на критику.

## Контроль объёма

- Перед любой задачей укажи `closes`: `roadmap:этапN-шагM` или `LG-YYYY-MM-DD-NN`.
- Задачи без `closes` или с неверным форматом не запускаются.
- Дополнительная работа идёт только через фильтр и журнал `docs/local-goals.md`.
- Изменение плана карты оформляется как RC в `docs/roadmap-changes.md`.

## Дисциплина токенов

- Не отправляй субагенту то, у чего уже есть готовый текст или патч: мелкую правку делай сразу.
- Ставя задачу субагенту, указывай точный список файлов и одну готовую команду, которая сразу выводит нужный кусок. Разведку по проекту делает постановщик, а не исполнитель.
- Задачу больше 30 минут или больше трёх файлов дели на две. Число шагов субагента конечно, и обрыв лимита означает повторный прогон целиком.
- Модели задаются совместно `opencode.json` и `.opencode/agents/*.md`; проверяй оба уровня. Не все роли дешёвые: сильное ревью стоит дороже и вызывается на ограниченную проверку. Kimi — подписка с конечной квотой, а не безлимит; использовать на сложной критике/ремонте, не на каждой команде. Автор и проверяющий не должны незаметно становиться одной моделью при fallback.
- Не тащи в основной контекст сырые страницы. Сначала `researcher`, при необходимости `digester`.
- Проси у субагентов таблицу, 5–7 фактов, ссылки и неопределённости, а не «расскажи всё».
- Не повторяй содержимое файлов в ответе — ссылайся на путь.
- Перед длинной сессией обновляй `STATUS.md`.
- Для простых задач не запускай субагентов.

## Контекстный поиск

- Выполняй поиск в трёх точках: перед выбором технологии или началом этапа; после неожиданного или отрицательного результата; при появлении новой информации.
- Формулируй вопрос с контекстом проекта: русский язык, CPU без CUDA, сроки этапа, доступное оборудование и ограничения по лицензиям.
- Ищи не только выбранное решение, но и альтернативы, ограничения и способ проверки.
- Оформляй результат как 5-7 фактов, ссылки с датой обращения и версией, ограничения, что проверить своим экспериментом, и рекомендацию.
- Источник не заменяет измерение: гипотезу из статьи проверяй прогоном.
- Источники вноси в `docs/sources.md`; лицензии кода, весов и данных проверяй отдельно.
- Дополнительную ветку по итогам поиска оформляй через `docs/local-goals.md`.

## Файлы

- `PROJECT.md` — замысел, границы, архитектура, метрики.
- `ROADMAP.md` — утверждённые этапы и дедлайны.
- `STATUS.md` — текущее состояние, следующие шаги, блокеры.
- `docs/sources.md` — реестр источников: ссылка, дата, версия, лицензия.
- `docs/raw/` — сырые выдержки для сжатия; не коммитятся.
- `docs/decisions/` — ADR: почему выбрано именно так.
- `experiments/` — эксперименты по шаблону.
- `reports/` — месячные и итоговые отчёты.
- `data/` — данные; не коммитить большие файлы и персональные данные.

## Правила работы

1. Для проектной задачи прочитай `STATUS.md` и relevant файлы; для простого вопроса или приветствия файлы не читай. Не пересказывай содержимое целиком.
2. Большую задачу разбей на шаги через `todowrite`.
3. Любой эксперимент: гипотеза, данные, конфигурация, seed, метрика, результат, ограничения.
4. Любой источник: ссылка, дата обращения, версия, лицензия.
5. Любое архитектурное решение: ADR с альтернативами и причиной.
6. Не расширяй обязательный объём без согласования с ментором.
7. Дорожная карта — утверждённая база, но не догма. Если новая информация или технология меняют план, оформи предложение в `docs/roadmap-changes.md`; не меняй `ROADMAP.md` без согласования.
8. Не обещай физические очки, gaze tracking, live-ASD или обучение большой модели с нуля, если это не согласовано.
9. Секреты — только в переменных окружения, не в файлах проекта.
10. Перед коммитом проверь `.gitignore` и отсутствие ключей.

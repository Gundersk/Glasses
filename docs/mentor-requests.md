# Задание ментора через владельца

`closes: LG-2026-11-13-01`. Обновлено 13.11.2026.

**Реализован ограниченный документный маршрут; живое качество ещё не проверено.**
Локальные тесты не дают допуска к произвольной ночи. Ничего не отправляется ментору,
карта не меняется, стадия не закрывается автоматически.

## Для владельца

В сессии OpenCode:

```text
/mentor-task <дословный вопрос или задание ментора>
```

Команда помогает оформить карточку и показать границы/цену/критерии. Это **не запуск**.
Для research перед показом карточки предписано короткое независимое reviewer-ревью
покрытия/запросов/границ, без поиска по теме. Это инструкция OpenCode-команде,
не машинная гарантия вызова; подтверждать фактическим ответом reviewer. Исполнимый
план всё равно отдельно проходит критика. Модельные вызовы подготовки в UI не
входят в денежный счётчик будущего Python-run: не выдавать его $0.50 за общий
гарантированный счёт подготовки и исполнения. Владелец может **одним сообщением**
согласовать показанную карточку и явно разрешить один запуск: второй формальной
команды не требуется. Простое согласование текста разрешением run не является.
Если вопрос можно ответить по имеющимся артефактам, достаточно краткого ответа со
ссылками; не нужно каждый вопрос превращать в цикл. Для обзора актуальных аналогов
потребуется поиск. При необходимости уточняется только недостающий результат или
срок, но не известное железо. Вызов команды в UI пока не проверялся.

Заготовка: `autonomy/workspace/requests/examples/analogues.json`. Она не выдаётся за
реальную дословную формулировку ментора и не зарегистрирована автоматически.
После согласования текста можно зарегистрировать без сети и LLM:

```powershell
.venv\Scripts\python.exe -m autonomy.intake submit autonomy/workspace/requests/examples/analogues.json
.venv\Scripts\python.exe -m autonomy.intake show MT-2026-11-13-analogues-v1
```

После **отдельной прямой команды владельца**, не сейчас, один запуск:

```powershell
.venv\Scripts\python.exe -m autonomy.intake run MT-2026-11-13-analogues-v1
```

Не запускать перед ним обычные `preflight`, `tick`, `start_night.ps1`: они работают
с другим STATE. Прямой `run` уже вызывает ограниченный runner с отдельными путями.
Не применять рабочий `AUTONOMY_MOCK` как способ изоляции. Требуются настроенные
провайдеры/поиск и доступная сеть; ошибки не обходить снятием проверок.

Если после submit изменились STATUS/контекст, show/run откажут: пересмотреть карточку
и создать новый id (`...-v2`), не подделывать старый хэш. Если уже создана папка run,
повтор этого id запрещён даже после обрыва. Сначала сохранить и проверить результат;
не удалять служебные файлы ради «продолжить».

## Карточка и границы

| Поле | Значение |
|---|---|
| `id` | `MT-YYYY-MM-DD-slug`, без переиспользования |
| `instruction` | точный текст владельца; происхождение — owner relay, не аутентифицированное сообщение ментора |
| `kind` | question / research / report / roadmap_change; measurement / code только для регистрации, не исполнения этим маршрутом |
| `closes` | существующий `roadmap:этапN-шагM` из scope либо активная зарегистрированная LG |
| `requirements` | 1–12 содержательных критериев ответа, видны автору и REVIEW |
| `research_queries` | до 3 безопасных строк, по 2 страницы; для research обязателен хотя бы 1 запрос |
| `budget_usd` | 0…1 USD, по умолчанию 0.5; локальный лимит, не гарантированный billing cap |
| `time_limit_minutes` | 2…30, по умолчанию 15 для ответа; отдельно 10 минут на сбор источников, до 50 минут на тик с воротами |
| `context_files` | до 5 дополнительных файлов docs/reports/experiments, md/json/jsonl |
| `research_policy` | только research; явное разрешение ограниченной адаптации и проверяемые темы, см. ниже |

Условия/сроки этапов берутся из PDF и scope, не из служебного реестра запроса.
Не следует обещать выполнение любого кода, установку пакетов, запись голоса,
принятие лицензии, новый платный сервис или изменение ОС по одному текстовому запросу.
Для этого нужен отдельный исполнимый протокол/решение владельца.

### Единый контракт лимитов (ADR-0008, 14.11.2026)

Для явного research_policy planner/critic/REVIEW получают свежий JSON:
allowed / used / remaining. `used=0` не означает запрет дополнительного раунда.
Запланированные и фактически запущенные запросы различаются.
Все сборы initial+followup делят 10 минут; все авторские попытки, fallback и
запись делят time_limit_minutes карточки (обычно 15 минут). Сумма рабочих часов
обычно 25 минут; 50-минутное окно координатора дополнительно включает ворота.
Ожидание подписочной квоты не рабочее время. Поздний ответ не принимается;
клиентский timeout не гарантирует отмены серверной генерации.
Проверки: `docs/audits/2026-11-14/limits-tests.json`; независимое ревью пока
не завершено. Это не разрешение запуска и не расширение legacy-карточек.

## Что делает система

С 14.11 (ADR-0011): новые research_policy-планы содержат --allow-unavailable и
typed-проверку research_collection. Известная недоступность выбранных URL
сохраняется manifest-ом с sources=[], unavailable_urls/error_codes и не мешает
следующей уже разрешённой команде. rc0 означает сохранённый исход, не прочитанную
страницу. При отсутствии всех реальных страниц автор не вызывается; при наличии
страниц достаточность/partial оцениваются прежними checks и смысловым REVIEW.
Auth/rate/network/MCP/schema/необъяснимые ошибки остаются fatal. Page/query caps,
receipt и approval сохраняются. Пустые manifests не дают supported claims.
Автоматического платного Exa/Perplexity fallback и скрытых повторов нет.

С 14.11 (ADR-0010): новые планы проверяют ответ typed-проверкой `mentor_response`
с привязкой ID к текущему runner. CLI `intake check` остаётся read-only диагностикой;
при дефектных claims возвращает JSON всех ошибок (claim_id/codes/URL/evidence_file),
не только первую. Плохой deterministic ответ возвращается автору без лишнего LLM
REVIEW; весь validation_feedback передаётся отдельно, без3000-char clipping.
Источники автору поступают отдельным пакетом <=60000 символов: все выбранные
страницы, точные адреса/хеши, непрерывные фрагменты и явные пропуски. Это не полные
публикации и не гарантия смысловой поддержки. Повторы делят прежние квоты/часы;
смысловой REVIEW обязателен для приёмки. Старые run не мигрируются и не переигрываются.

1. Сохраняет `request.json`, контекстную записку и SHA-256 входных документов.
   Правка записки/карточки/контекста снимает допуск. Это защита от случайной
   подмены, не криптографическая аутентификация и не OS sandbox.
2. Строит фиксированный план именно под запрос, независимо от текущей T2-цели.
   Критик получает запрос, нормативный артефакт и проектный контекст. При block
   или сбое — остановка. Legacy без research_policy останавливается и на revise.
   С research_policy исправимые запросы может предложить planner один раз;
   только JSON queries/reason, никакого редактирования поручения/команд/лимитов.
   Новый план обязательно возвращается независимому критику. Независимость
   проверяется по фактической модели автора и критика, не алиасу.
3. Если нужен поиск, выполняет точные approved_commands без executor LLM,
   с обходом кэша (`--fresh`), сохраняет страницы/URL/дату и receipt команд.
   «Не удалось прочитать страницы» — не доказательство и не готовый обзор:
   legacy останавливается; policy различает typed ресурсную недоступность и fatal.
   Перед fetch
   выполняются дедупликация URL и эвристический отбор по релевантности/разнообразию
   доменов из первых 20 результатов; manifest сохраняет отбор/отказы. Подсказка
   repository/docs/arxiv не доказывает первичность или достоверность. Для legacy
   критик может запросить 3 уточнения; с research_policy скрытый поиск критика
   отключён, все тематические поиски проходят утверждаемый сбор и общий cap.
4. Автор получает документы и источники; пишет **только** три файла ответа.
   Команды от автора, правка источников, STATE/approval и канонических документов
   запрещены. Если сбор источников не принят или они изменены — ответ не принимается.
5. Проверяет структуру решения, наличие claim id/URL и точной цитаты в сохранённой
   странице. Research требует минимум 2 supported claim; это не обещание двух
   независимых источников и не критерий достаточности научного обзора.
   С research_policy дополнительно обязательны min_sources разных нормализованных
   URL, min_domains и decision.coverage по всем topics со ссылками на supported
   claim IDs. Это проверка покрытия ссылками, не смысла цитат и не полноты науки.
6. Независимый REVIEW использует сильную лестницу критика из config, получает
   запрос, ответ, claims/decision и ограниченные тексты страниц. Другая модель,
   чем автор; Kimi-квота общая (до 8 физических попыток). При сомнении — эскалация.
   Истинность вывода, полнота поиска и пригодность данных не доказываются одной цитатой.
   REVIEW получает и страницы сбора источников. Для policy-поручения он может
   предложить SEARCH с новыми запросами и причиной пробела. Код проверяет пределы,
   неизменность прежних receipts и создаёт только дополнительные команды сбора.
   Прежние команды не повторяются; новый план опять проверяет другой критик.
   Исправимые ошибки текста проходят FAIL → повтор автора, не бесконечный REPAIR.
   Счётчик попыток ответа общий на всё поручение, а не сбрасываемый при новом плане.
   Если рамок не хватило, автор может явно указать completion_status=partial:
   это НЕ смягчение критериев полного результата. Формат частичного материала
   описан ниже; финальный REVIEW должен вернуть PARTIAL, а не PASS.
   Для финального REVIEW передаётся отдельный пакет всех supported-цитат с
   окружающим текстом (до 1000 символов с каждой стороны), а не только начало
   evidence JSON. Если цитата отсутствует/слишком велика или пакет >60k символов,
   PASS запрещён: ограниченная доработка ответа или остановка. Контекст соседства
   не заменяет чтения всей публикации, при недостаточности — сомнение/эскалация.
7. Пишет отчёт и digest в отдельный run; не запускает manager/replan и не меняет
   канонические цели. Ошибка/лимит оставляют понятную точку решения владельцу.

### Явная рамка адаптивного исследования

```json
"research_policy": {
  "topics": ["предшествующие работы по задаче", "альтернативы и условия сравнения"],
  "max_queries": 6,
  "pages_per_query": 2,
  "max_plan_revisions": 1,
  "max_followup_rounds": 1,
  "answer_attempts": 2,
  "min_sources": 3,
  "min_domains": 2
}
```

Темы конкретизируются под поручение, не копируются механически. До 3 начальных
запросов + резерв укладываются в общий max_queries (не более 6); каждый запрос
читает максимум pages_per_query (не более 3) страниц. Два домена не означают две
независимые научные работы. Пороги считаются по реально использованным supported
цитатам, а не просто найденным ссылкам. Поисковый сервис может вернуть мало страниц:
нельзя объявлять невозможным провал или полноту по одному количеству.

Исходная карточка/requirements/closes/бюджет неизменны. Оркестратор сохраняет
цепочку `run/research-plan-NN.json`, связанную с хэшем карточки и предшествующей
версией; approval учитывает её хэш. Новые планы имеют новые inputs/receipts,
завершённые источники и их доказательства сохраняются. Выполняются только фиксированные
команды builder, не строки команд от моделей. Общий денежный бюджет, квотные caps,
50-минутное окно тика и запреты отправки/карты сохраняются. Повтор после падения
процесса по-прежнему не разрешён автоматически.
Обновление сопровождается `research-update.pending.json`: новая версия → атомарная
запись плана → STATE → снятие маркера. Любой незавершённый префикс оставляет
approval недействительным и recovery переводится в REPORT, без повторения источников.
Невалидный JSON/тип/null ответа контролёра — ESCALATE, не исключение или PASS.

Старые карточки без research_policy **не получают автоматически дополнительный
расход**. Для нового разрешения готовится новая согласуемая версия, не правка
хэша старой. Это касается и существующего черновика литературного обзора:
в этой сессии он не регистрировался и не выполнялся.

### Полный, частичный и заблокированный исход

- **complete:** исходные минимумы источников/доменов и подтверждённое покрытие
  каждой темы, проверки и REVIEW=PASS. Это полный черновик, не отправка/закрытие этапа.
- **partial:** в decision.json `completion_status: "partial"`, непустой список
  `limitations`; в response.md явная надпись **ЧАСТИЧНЫЙ РЕЗУЛЬТАТ** и ограничения.
  В coverage перечисляются ВСЕ исходные темы; для непокрытой — `claim_ids: []`
  и непустой `gap`. Код сохраняет также дефициты min_sources/min_domains.
  Все имеющиеся supported-утверждения всё равно требуют настоящих сохранённых
  цитат/URL. Финальный REVIEW=PARTIAL и успешные проверки структуры/цитат дают
  статус задачи `partial`, исход поручения `partial`, список пробелов в отчёте
  и digest. Не `done`, не PASS полного обзора и не новое требование к карте.
- **blocked:** нет принятого полного или частичного материала (например, ошибочные
  цитаты, не принят сбор источников, не хватило квоты на REVIEW, сбой/нет ответа).
  Уже записанные черновики сохраняются, но не называются проверенным partial.

Минимумы и полнота не понижаются для complete. Partial допускается только в
research_policy-маршруте, не для legacy или успешности команд сбора. Автор и
контролёр должны согласовать исход: PASS не превращает partial автора в done;
PARTIAL не может задним числом объявить полный ответ корректным частичным.
При доступном полезном поиске контролёр может предложить SEARCH внутри прежних
лимитов. После принятого partial запуск заканчивается, автоматического расширения
бюджета/отправки/закрытия этапа нет. Если лимит исчерпан до создания или проверки
черновика, нельзя обещать проверенный частичный ответ «из ничего» — исход blocked.

Пример непокрытой темы в `decision.coverage`:

```json
{"topic": "точная тема из research_policy.topics", "claim_ids": [],
 "gap": "Первичный источник не прочитан в пределах разрешённого поиска"}
```

Один общий lock исключает одновременную работу с обычной ночью. Модель может
записывать только три файла ответа; системные команды всё равно имеют права
пользователя. Нет гарантий стоимости/времени отдельного внешнего API сверх таймаута
и ограничений клиента, нет гарантии качества до живой калибровки.

## Где результат и как его читать

- `reports/mentor/<id>/response.md` — черновик ответа по критериям;
- `claims.json` — supported/unverified, claim id, URL, цитата, путь сохранённой страницы;
- `decision.json` — нужны ли изменения карты/отчёта, почему и что делать владельцу;
- `autonomy/workspace/requests/<id>/sources-*.md.json` — текст страниц и дата;
- `.../<id>/run/` — STATE, цели только этого запроса, plan/approval, evidence,
  verdicts, events, `outbox/report.md`, `outbox/facts.json`, `digest.md`.

`roadmap_change: true` требует проверенного факта, триггера (железо/лицензия,
нет эталона, опровергнута посылка, prior art, риск срока), причины и варианта
`no_change`. Это **предложение**, а не согласование. Владелец затем решает,
нужен ли RC в уже существующем `docs/roadmap-changes.md` и ADR для архитектуры.
Если достаточно уточнить отчёт, карта не меняется. Перед отправкой проверить
утверждения/источники, метрики/ограничения и реально существующие артефакты.

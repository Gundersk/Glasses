- summary стирает подробности старой части; инструкции перечитываются в текущей

- background может расходовать токены на неиспользованную сводку, warming —
  отдельные transient-запросы. Их выключение здесь обосновано экономией;
- кастомный prompt сводки в проверенных страницах не подтверждён. Не выдумывать

потери сложных решений. Нельзя заключить, что именно она вызвала прежние сбои:

## 2. Ночная внутренняя система

Это не длинный диалог с периодической суммаризацией. Каждая роль получает
новый messages-пакет; OpenAI-адаптер создаёт новую сессию на каждый вызов,
загружает JSON списка сообщений как instruction entries чанками5000 символов
и делает один generate. История основной сессии ночным моделям не передаётся.
Fallback также не наследует «память модели»: его вход строится кодом.

Долговременная память — STATE, карточка, plan/revision chain, receipts, verdicts,
digest, источники/ADR. Это плюс для проверяемого восстановления. Но факт хранения
файла не равен факту включения нужного раздела в конкретный модельный вход.

| Материал planner | Размер сейчас, символы | Срез | Не передаётся |
|---|---:|---:|---:|
| STATUS | 53701 | 4000 | 49701 |
| agent-context | 11361 | 12000 | 0 |
| PROJECT | 6440 | 2000 | 4440 |
| benchmarks | 8496 | 1800 | 6696 |

Срезы помечены `(обрезано)`: это не скрытое усечение. Однако код не доказывает,
что все обязательные текущие условия попали до среза. STATUS начинается с текущего
состояния, поэтому нельзя заявлять, что новости обязательно потеряны.
agent-context почти исчерпал12k, а продолжает расти историческими вставками.
Для обычных inputs пофайловый лимит8k, для карточек24k. Авторский source-пакет
и quote-пакет REVIEW <=60k с явными omissions/fail-closed — более надёжный подход,
чем source JSON prefix, но не универсальное решение остальных входов.

REVIEW: context JSON с checks/diff обрезается после сериализации до12k;
response/claims/decision читаются до24k каждый. response имеет structural cap24k,
но совокупный claims JSON и decision могут быть больше. Требуется проверка
полноты обязательных компонентов до вердикта. **На v5 потери этих трёх файлов
не было:** 15322/4232/3340 символов, все меньше24k. Это риск других входов,
не установленная причина ошибок v5.

OpenAI input guard использует UTF-8 bytes + запас/выход, не токенизацию полного
запроса. Он fail-closed, но не измеряет полноту/релевантность. В остальных
provider-ветках len(chars)//4 — оценка стоимости, не единая гарантия вместимости.
Кроме того, role-JSON в instruction entries восстанавливается текстовой просьбой
модели, а не передаётся нативной историей ролей. Устойчивость к инструкциям внутри
источников нужна отдельным тестом, увеличение keep её не исправляет.

## 3. Приоритет изменений (предложения, не выполненная настройка)

1. **Первым — структурированный handoff**, а не больший keep: цель/closes,
   текущий шаг/исход, разрешено/запрещено, решения/причины, неподтверждённое,
   следующие действия, пути и hashes доказательств. Актуальная краткая часть
   отдельно от исторического STATUS. Обновление кодом по STATE где возможно;
   summary никогда не повышает статус результата.
2. **Единый context manifest для night:** фактические разделы/размеры/срезы,
   source hashes и omitted sections. Критические поля передаются целиком либо
   вызов блокируется. REVIEW не может PASS по обрезанным обязательным JSON.
3. **Калибровка на фиксированных случаях:** ограничения, незакрытый run,
   source vs measured, несогласованная RC, секреты/инъекции, длинные claims/diff.
   Проверить recovery после checkpoint без новых тематических прогонов. Только
   затем оценивать модель-компактор/keep/buffer по сохранённым фактам и расходу.
4. Внешние keep24k/summary/background=false/warming=false **пока сохранить**.
   Возможный эксперимент buffer25–30% даст запас для compaction на меньших окнах,
   но увеличит частоту/расход; не считать улучшением до теста. Не возвращать
   глобальные75% в проект — это гораздо более раннее и частое сжатие.
5. Модель-компактор закрепить проектно после калибровки и задать проверенный
   output cap; не переносить слепо на browser-модель/native. Универсальный cap
   без учёта модели/языка и структуры сводки также не гарантия сохранности.
